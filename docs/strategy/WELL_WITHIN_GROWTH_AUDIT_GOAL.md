# Well Within Growth Audit Goal

## Critique of the original prompt

The original prompt is unusually strong: it connects content and product, requires current evidence, distinguishes model roles, protects production systems, and defines verification and stop conditions.

The main improvements needed were:

1. **Define implementation scope.** “Produce and implement an optimization plan” could authorize anything from documents to major app changes. The revised goal limits implementation to safe, high-confidence local improvements and treats larger product or positioning choices as recommendations.
2. **Make completion measurable without private analytics.** The revised goal requires repository artifacts, citations, before/after automation records, checks, and explicit missing inputs rather than implied growth outcomes that cannot yet be measured.
3. **Separate evidence levels.** Observed facts, reasoned interpretations, and recommendations must be labeled so competitor patterns and market assumptions are not presented as proven results for Well Within.
4. **Ground model routing in available tooling.** Sol/Terra/Luna are retained as an operating preference where automation tooling exposes those models, but research roles and quality standards—not model names alone—define the work.
5. **Protect the existing working tree.** Current social strategy files contain active uncommitted work. The revised boundaries favor new dated audit artifacts and narrowly scoped edits, preserving unrelated or user-authored changes.
6. **Add health-domain safeguards.** The audit may assess clarity and trust, but it must not invent clinical claims or treat marketing strategy as medical advice.

## Revised executable goal

/goal Produce an evidence-backed Well Within growth and product audit, implement the safest high-confidence local improvements, and leave a prioritized plan for changes that require analytics, credentials, or product approval.

Verification: inspect repository code, project documentation, design/content assets, local automation definitions, and public market/competitor evidence; cite current web sources; reference exact local artifacts; save a dated audit package in the repository; provide before/after records for any automation changes; and run the smallest relevant project checks plus visual/runtime verification for any code changes.

Constraints: distinguish observed facts, reasoned inferences, and recommendations; do not invent analytics, medical claims, or market evidence; preserve current product behavior and brand intent unless a finding justifies a scoped change; do not deploy, publish, buy ads, alter public accounts, delete automations, or make irreversible changes.

Boundaries: write only to directly relevant Well Within strategy/content documentation, local non-production workflow or automation definitions, and narrowly related app files/tests; do not modify credentials, production infrastructure, generated iOS dependencies, release configuration, or unrelated modules.

Iteration policy: work in discovery, public research, diagnosis, implementation, and verification passes; make one focused change at a time; after meaningful changes rerun relevant checks and inspect new evidence; use at most three focused improvement rounds; delegate only narrow evidence-gathering work.

Stop when: the repository contains a clear current-state diagnosis, actionable social/content strategy, prioritized app/product roadmap, reviewed automation plan with safe local changes completed, a now/next/later backlog, citations, and verification results; all missing private inputs and unresolved risks are explicit.

Pause if: completion requires private analytics or account access, credentials, paid tools, production changes, public publishing, legal or clinical approval, destructive actions, or a product-positioning decision whose alternatives materially change the work.
